# 한영타 판정 실측 검증

한영타 판정(`HangulConverter.analyze` → `TypoLanguageModel.judge`)의 규칙·파라미터는 **감이 아니라 공개
데이터 실측으로 정한다.** 이 문서는 그 데이터, 돌리는 방법, 기록된 수치, 그리고 규칙을 정한 실험 과정을
남긴다. 규칙을 바꾸면 같은 방법으로 전후를 비교하고 아래 기록을 갱신할 것.

## 0. 판정 구조와 점수 읽는 법 (2026-09 재설계)

라틴 토큰(공백·한글로 끊은 영문 조각) 하나를 두 **한영타 가설**로 읽고, 각 가설을 세 **대안 설명**과
맞붙인다.

| 한영타 가설 | 읽는 법 |
|---|---|
| CapsLock 꺼짐 | 원문 그대로 두벌식 변환 (`dkssud` → 안녕) |
| CapsLock 켜짐 (대문자가 과반일 때만) | 대소문자를 뒤집어 변환 (`DKSSUD` → 안녕, `GOtEK` → 했다) |

| 대안 설명 | 모델 | 잡는 것 |
|---|---|---|
| 영어 단어 | 영어 글자 trigram | `work`(→재가), `hello` |
| 한국어 글 속 알려진 라틴 문자열 | Shift 증인 사전(849개) | `sns`(→눈), `dlc`, `fps`, `snl` |
| 약어 | 약어 글자 bigram | 사전에 없는 약어·모델명 `cmd`, `SBTi` |

가설마다 **가장 강한 반론을 상한**(min)으로 삼고, 두 가설 중 나은 쪽(max)이 그 토큰의 신뢰도다. 선택
전체의 신뢰도는 토큰들의 최댓값.

- **영어 단어와의 비교**는 예전 점수 그대로다: `(한국어 로그확률 − 영어 로그확률) ÷ 영문 글자 수`.
  로그확률은 0에 가까울수록 흔하고 음수가 클수록 드물다(1 차이 ≈ 2.7배). 양수면 한영타 쪽이 그럴듯하다.
  글자 수로 나누는 건 긴 단어가 무조건 유리해지지 않게 하기 위해서다.
- **사전·약어와의 비교**는 로그오즈 그대로(글자 수로 나누지 않음) — "한국어 어절로서의 빈도"와 "한국어
  글 속 라틴 토큰으로서의 빈도"를 직접 견준다. ⚠️ 이 둘을 영어 쪽 확률에 그냥 섞으면(`P_영어 + β·P_사전`)
  글자당 척도와 안 맞아 사전 항목이 전부 차단된다(실측: 한 음절 한영타 감지 81%→54%). 그래서 상한 구조다.
- **Shift 물리**: 두벌식에서 Shift 가 의미 있는 키는 Q·W·E·R·T·O·P(쌍자음 ㅃㅉㄸㄲㅆ·복합모음 ㅒㅖ) 뿐이다.
  그 외 키의 대문자(`sNl` 의 N, `CoA` 의 A)는 한글을 치던 사람이 누를 이유가 없으니 **반대 증거**(벌점),
  Q·W·E·R·T·O·P 대문자만 있으면 가산. CapsLock 가설에선 같은 규칙을 소문자에 적용한다.
- **한국어 문맥**: 선택 앞뒤 40자(선택 포함)에 한글이 있으면 "영어 단어" 가설만 불리하게 한다 — 첫 글자가
  그 가설로 칠 수 있는 모양(CapsLock 꺼짐 = 소문자 또는 Q·W·E·R·T·O·P 대문자 / 켜짐 = 대문자 또는 그 키의
  소문자)이면 로그오즈 **11.0**(2026-09-30 에 10.0, 2026-10-01 어절 2-gram 뒤 11.0), 아니면(`Dirk`·`Duden` 같은
  대문자로 시작하는 이름) 예전 값 3.0 만.
  사전·약어는 원래 한국어 글에서 센 값이라 그대로. 영어 문서(주변 한글 없음)의 판정은 이 값과 무관하다.
- **구어체 낱자모(2026-09-29)**: 토큰 안에서 음절 **뒤**에 오는 자음 낱자모와 `ㅠ`·`ㅜ`·`ㅡ`(`재밌음ㅋㅋ`,
  `있어요ㅠㅠ`)는 최저 확률 대신 구어체 전이 표(교체 단계가 쓰는 NSMC train 단위 전이)로 채점한다. 음절
  앞머리 낱자모(`ㅡ도야`=Mehdi)·낱자모만인 토큰(`zzz`, `bbbb`)·모음 반복(`sooooo`→내ㅐㅐ)·CapsLock 가설
  (`AHHHHH`→뫃ㅎㅎㅎ)은 그대로 최저 확률 — 전부 실측 오탐으로 나와 뺐다.
- **한국어 쪽 점수(2026-10-01)**: 여러 음절 덩어리는 어절 안 음절 2-gram(`^너`·`너무`·`무$`, Kneser-Ney, 이득순
  10만 쌍)으로, 한 음절 어절은 '홀로 쓰인 음절' 분포로 잰다. 어절 맨 앞 자음 하나 + 음절(`ㅈ같은`, ㅋ·ㅎ 제외)은 구어체
  전이로 채점한다. 근거는 4.11.
- **주변 한글이 없을 때(2026-10-01)**: 두 한영타 가설에 logit(0.70) − logit(0.45) 를 더해 경계를 낮추고, 흔한 영어
  단어(자동 보호 목록 44개)는 판정하지 않는다(4.10).
- **주변 글 증거(2026-10-01)**: 앱이 넘겨주는 주변 글(선택 앞뒤 40자)로 ① 라틴 이웃의 한영타 확률(편집 칸은 올리기만,
  읽기 전용 글은 양쪽) ② 문장 중간의 무의미한 첫 대문자 벌점(`Dhaka`) ③ 문장 첫머리 자동 대문자 가설(`Dkssud`)을
  더한다. 근거는 4.11.
- 마지막에 전체 로짓을 0.2620 민다 — 예전과 같은 영어 오탐 수준(영어 기사 ≤ 75, 사전 47만 단어 중 ≤ 102)이
  설정 기본값 70% 에 오도록(4.10·4.11 이후로는 그 수준보다 감지 쪽에 있다).

## 2. 돌리기

```bash
tools/eval-data/fetch.sh
./gradlew testDebugUnitTest --rerun --tests "com.langsense.app.eval.*" -i   # -i 로 수치 출력
```

⚠️ `--rerun` 을 빼면 코드가 안 바뀐 경우 Gradle 이 "최신 상태"로 보고 테스트를 건너뛴다(데이터 폴더는
Gradle 이 추적하는 입력이 아니다) — 데이터를 받은 직후 수치가 안 찍히면 이것 때문이다.

표를 다시 만들 때(`TypoTables.kt` 는 손으로 고치지 않는다):

```bash
tools/typo-model/fetch_corpora.sh && tools/eval-data/fetch.sh
python3 tools/typo-model/build_tables.py     # pyarrow 필요, 약 3분
```

생성기의 `score()` 는 Kotlin 판정의 파이썬 이식이다(판정에 영향을 주는 증인 사전 항목을 고를 때 쓴다) —
판정식이나 매개변수를 바꾸면 둘을 같이 바꿀 것. 2026-09 에 Kotlin 판정과 파이썬 이식을 토큰 5천 개
(한영타·영어 기사·영어 사전·한국어 글 속 라틴·CapsLock, 문맥 있음/없음)로 대조해 최대 오차 5×10⁻⁷ 로
일치함을 확인했다. 2026-10-01 에는 토큰 5,650개 × 판정 방식 4가지(문맥 없음 / 한국어 문맥 / 문장 중간 / 이웃 확률용 순수 모델)와
실제 글 선택 7,001건(주변 글 규칙 전부 포함 — 이웃·자동 대문자·보호 목록 해제)을 대조했다: 최대 오차 5.3×10⁻⁷,
70% 경계 뒤집힘 0. 생성기는 같은 입력이면 바이트 단위로 같은 `TypoTables.kt` 를 만든다(두 번 생성해 비교).

## 4. 재설계 과정에서 확인한 것

1. **가장 많이 놓친 한영타는 가장 흔한 짧은 단어였다.** 재설계 전 NSMC test 누락 1위가 `sjan`(너무,
   2,803회), 이어 `rmsid`(그냥)·`dho`(왜)·`wha`(좀)·`sork`(내가). 음절을 서로 독립으로 보는 모델은 "너무"가
   통째로 흔한 단어라는 걸 몰라 P(너)×P(무) 로 실제보다 약 e⁸ 배 낮게 봤다. → 음절마다 어절 안 위치(홀로·
   첫·가운데·끝) 확률을 따로 두고, 상위 1천 어절은 실제 빈도와 반반 섞었다(1천 개와 3천 개가 같은 성능,
   1만 개도 +0.1%p). 한 음절 어절은 "홀로" 위치 확률이 곧 그 어절의 빈도라 따로 기억할 필요가 없다.
2. **한국어 글 속 라틴 토큰의 오탐은 대부분 소문자 약어였다.** 스팀 리뷰 10만 건에서 `dlc` 432회·`fps`
   143회, 댓글·챗봇의 `sns`, 리뷰의 `snl`. 영어 모델은 단어로 학습돼 모음 없는 약어를 매우 드물다고 본다.
3. **Shift 증인**: 한국어 글에서 이 약어들은 대문자로도 쓰인다(`SNS` 1,092회, `FPS` 91회, `DLC` 19회 —
   학습 분할). 한글을 치다 보면 Shift 무의미 키의 대문자는 나올 수 없으므로, 그런 모양이 한 번이라도 나온
   문자열은 **라벨 없이** 진짜 라틴 문자열로 확정된다. 학습 분할 원문의 라틴 토큰 77만 회에서 1.9만 개가 채굴됐고, 그중
   소문자로 써도 모델이 한영타로 기우는(신뢰도 30% 이상) 것만 앱에 담았다(643개 → 구어체 낱자모 반영 후 749개 → 2026-09-30 750개 → 구어체 보강 후 736개 → 2026-10-01 문맥 없는 판정 강화 후 867개). 무조건 차단하면 `dlf`(DLF↔일)
   `alc`(ALC↔및)처럼 흔한 한글과 겹치는 것까지 막혀 한영타 감지가 1.6%p 떨어져서, 빈도로 저울질한다.
4. **3글자 라틴 토큰의 약 70%가 전부 대문자 약어**(한국어 글 기준; 영어 기사는 4%). 전부 대문자를
   뒤집어 보기만 하면 3글자는 10%, 4글자 1%, 5글자 0.5% 가 오탐 → 3글자는 CapsLock 가설에 추가 벌점(−2)을
   줘 사실상 제외했다. 대신 실제 대문자 약어는 한글로 바꾸면 깨진 자모가 되고(글자당 약 −20) CapsLock
   한영타는 멀쩡한 한글(글자당 약 −3)이라, 4글자부터는 간격이 넓어 안전하게 잡힌다.
5. **약어 모델은 차수가 중요하지 않았다**(unigram·bigram·trigram 성능 동일) → 가장 작은 bigram(729칸).
   단, 학습 데이터에서 `REUTERS` 같은 대문자 일반 단어를 섞은 채 "약어"로 쓰면 긴 CapsLock 한영타까지
   약어로 설명돼 CapsLock 감지가 17% 로 무너진다 — CapsLock 가설의 영어 쪽은 "대문자로 쓴 일반 단어 30% +
   약어 70%" 혼합에 글자당 보정(+3.0)을 둔다.
6. **약어 뒤 꼬리는 어절 끝 위치로 채점한다.** `CGrk`(CG가)의 `가`를 "홀로 쓰인 어절"로 채점하면 조사라
   확률이 바닥이 돼 약어+조사 감지가 91% 로 떨어졌다. 또 꼬리 안의 Q·W·E·R·T·O·P 대문자(`SFdudghkrPdml`
   =SF영화계의)를 허용해야 한다 — 예전엔 "무조건 +2.0" 이 가려 주던 경우다.
7. **구어체 낱자모(2026-09-29)**: 재설계 후 남은 누락 중 낱자모가 섞인 한영타(`재밌음ㅋㅋ`, `있어요ㅠㅠ`)는
   12.1%만 잡혔다 — 감지 모델이 정제된 글로 학습돼 낱자모를 전부 최저 확률로 봤기 때문. 교체 단계가 이미 쓰는
   구어체 전이 표를 감지에도 쓰되, 적용 범위는 **오탐 실측으로 좁혔다**: 처음엔 모든 낱자모에 적용했더니

   오탐으로 나왔다. 그래서 "토큰 안에서 음절 뒤" + "자음과 ㅠㅜㅡ만" + "CapsLock 가설에선 끔" 으로 제한했다.

   - 앞머리 자음: 모든 글자에 문맥 가산(+10) → P 78.3% 지만 B 74.63→72.82%(`3d를`→`3ㅇ를`, `x같은`→`ㅌ같은`, `TV물`) 기각.
     글자별 실측 로그오즈(양수인 글자만 가산) → P 76.8%, B 73.63% 여전히 하락 → "그 토큰 자체가 한영타로 판정될 때만"
     (`ram`→`ㄱ므` 단위 테스트 실패도 함께 해결) → P 58.0%, A·L·B 전부 유지(B +0.03%p).
   - 자동 대문자 읽기: 판정에서 이기면 무조건 소문자로 읽기 → A 97.19→94.00%, B 74.6→70.2% 기각(`찐짜`→`진짜`,
     `That's`→`that's`). 라틴이 남는 토큰 제외 + 한국어 로그확률 비교 기준 0.7/2/4/6/8/10 → 자동 대문자 문장 정확 교체
     95.7/95.1/93.8/91.5/87.6/79.9%, A 96.54/96.87/97.04/97.12/97.16/97.18%. **10 채택** — 외장 키보드 입력에 자동
     대문자가 실제로 붙는지 실기기 미확인이라(붙지 않는 환경이면 첫 대문자는 일부러 누른 Shift) A 손실이 거의 없는 쪽을
     골랐다. 확인되면 2~4 가 낫다. 남은 자동 대문자 실패 8,735건 = 기준 미달로 쌍자음이 남은 것 7,333(`찌루하지는`) +
     소문자로 쳐도 틀리는 IME 모호성 1,207 + 기타 195.

   **비용**: 노드 IPC 추가 없음(편집 가능 여부·inputType 은 노드에 이미 담긴 값). JVM 에서 선택 1회 판정 3.7µs → 6.5µs
   (주변 한글이 없을 때만 이웃 판정, 실기기 미측정). 2-gram 표는 문자열 약 22만 자(키는 정렬된 차이를 45진 가변 길이로,
   값은 91단계 양자화) — 처음 판정할 때 한 번 풀어 힙 약 0.5MB(키 IntArray 400KB).

   **구현 메모**: ① 생성기(`build_tables.py`)의 `Model.ko` 와 Kotlin `koreanWordLogProb` 는 한 줄씩 같다(증인 사전·보호
   목록을 이걸로 고른다). ② 생성기는 집합 순회를 정렬해 같은 입력이면 같은 바이트를 낸다(예전엔 파이썬 해시 순서로
   `BIGRAM_LO/HI` 마지막 자리가 흔들렸다). ③ 6만 자 상수를 100자 조각 600개의 `+` 로 이으면 Kotlin 컴파일러가 간헐적
   내부 오류(IrConstTransformer)를 내서 2-gram 조각은 2,000자 단위로 쓴다.

   뒤 전환. 오탐 = 실제 리뷰에서 영문 뒤 한글이 오는 2,407자리(일부러 영어를 치고 전환 — 진짜 한영타도 섞여 있다).

## 5. 남은 과제 (발견만 하고 아직 안 고친 것)

- **대문자로 쓰인 적 없는 소문자 라틴 단어**: 게임 장르 `aos`(→맨, 스팀 14회)·`soso`(쏘쏘→내내 — 강한 문맥
  가산 뒤로 한국어 문맥에서 89%). 학습 글에 대문자 모양이 없어 증인이 없다 — 사용자가 설정의 **예외 단어**
  (또는 "교체?" 칩 길게 누르기)로 막는다.
- **한국어 글 속 외국어 낱말**: 위키의 `cosh`·`aus`·`ans`·`(shah)` 처럼 영어가 아닌(또는 드문) 라틴 낱말이
  한국어 문맥에서 오탐(강한 문맥 가산의 대가, 10.3만 회 중 12회).
- **희귀 상표·아이디**: `Qorvo`(→빽패), 아이디 `sjco`(→너채) 등 한두 번 나오는 것.
- **문맥 없는 짧은 모호어**: `rid`(걍 — 실제 영단어)·`wha`(좀)는 보호 목록이라 단독 선택이면 안 잡히고(주변이
  한영타면 잡힘), `dir`(약 — 흔한 약어)은 반대로 단독 선택이면 78% 로 오탐이다. 한국어 문맥이 있으면 대부분 잡힌다
  (한 음절 95.8%).
- **읽기 전용 영어 글 속 한영타 한 단어**(2026-10-01, 이웃 증거의 대가): 남이 쓴 영어 글에 한영타 한 단어가 섞이면
  영어 이웃이 끌어내려 약 67% 만 잡힌다(편집 칸은 99.3%).
- **어절 앞머리 자음**(2026-10-01): `tqkf`(ㅅ발)는 감지되지만 `t발` 로 바뀐다(데이터상 `t` 는 라틴 접두어가 더 흔하다).
  `wakdrpa`(ㅈ망겜)처럼 뒤 음절 조합이 드물면 감지 자체가 안 된다(1.4%). 교체는 그 토큰이 스스로 한영타로 판정될 때만
  해서(`ram`→`ㄱ므` 방지) P 58% — 이 제한이 없으면 77% 였지만 영어 섞인 리뷰가 나빠졌다.
- **자동 대문자 읽기 기준(10)**: 실기기에서 외장 키보드 입력에 자동 대문자가 붙는지 확인되면 2~4 로 낮춰 자동 대문자
  문장 정확 교체를 79.9 → 93~95% 로 올릴 수 있다(4.11).
- **단독 선택한 영어 고유명사**: `Dhaka`(77.9%)·`Goran` 처럼 주변 글 없이 한 단어만 선택하면 여전히 오탐이다(영어
  문장 속이면 주변 글 규칙이 막는다 — 4.2%).
- **3글자 CapsLock 은 일부러 미지원**(`DKS`=안): 같은 모양의 약어가 압도적이라서. 4글자 이상은 97%.
- **`zzz`(ㅋㅋㅋ) 단독 선택은 감지하지 않는다**: 낱자모만인 토큰은 조는 소리 `zzz`·엄지척 `bbbb` 와 모양이
  같아 여전히 최저 확률이다. 음절 뒤의 `ㅋㅋ`(`woalTdmazz`=재밌음ㅋㅋ)는 2026-09-29 부터 잡는다.
- **받침으로 붙는 자음 반복**: `whgspdygg` 는 두벌식 조합상 `좋네욯ㅎ` 이 된다(실제 IME 도 같다) — `욯` 이
  드문 음절이라 감지하지 않는다. 사람이 이렇게 친 원문도 `욯ㅎ` 이라 본질적으로 모호하다.
